1. 设计目标与解决痛点

在对 RocketMQ 底层组件（如 RocksDB 版本升级、ConsumeQueue 存储结构、Timer/Transaction 引擎、元数据 ConfigStorage V2 等）进行改动时，单测与短生命周期集成测试往往无法暴露以下深水区问题：

  • 跨进程边界与真实启动链路缺失：嵌入式测试共享同一 JVM 内存与类加载器，无法真实模拟 OS 进程级信号（SIGTERM / SIGKILL）下 PageCache / RocksDB WAL 刷盘与冷启动恢复。
  • 混合负载耦合效应：普通消息、严格顺序消息、定时时间轮/RocksDB Timer、分布式事务半消息回查、Pop 消费同时读写时，对共享存储（CommitLog 与 RocksDB 多 ColumnFamily）产生的并发干扰。
  • 只压吞吐、不验内容：传统 Benchmark 仅统计 QPS/RT Counter，无法发现小概率的「丢 1 条消息」、「Payload 字节错位」、「局部乱序」或「已回滚事务半消息被误投递」。
核心设计理念： 将「独立 OS 进程集群管理」、「多模型混合负载生成」、「周期性进程级故障注入」与「单消息粒度真理账本（Ground-Truth Ledger）」解耦并闭环，任何一处违反端到端不变量立即判定失败并输出结构化诊断报告。

3. 五维正确性真理账本 (CorrectnessLedger)

CorrectnessLedger 是整个 LongRunning 框架的核心裁判器。每条由框架生成的消息在发送前均注入自包含的校验属性头与确定性二进制载荷： 

// 消息自描述属性头 (User Properties)
LR_RUN_ID              = "lr-ce7decc6"                  // 批次唯一标识，隔离不同运行实例
LR_MSG_KEY             = "lr-ce7decc6-FIFO-fifo-key-2-18" // 全局唯一消息主键
LR_WORKLOAD            = "NORMAL | FIFO | DELAY | TRANSACTION | POP"
LR_SHARD_KEY           = "fifo-key-2"                   // 分区顺序键
LR_SEQ_ID              = "18"                           // 单调递增序列号 (0, 1, 2, ...)
LR_CRC32               = "3849104721"                   // 发送端计算的 Body CRC32 校验和
LR_SEND_TS             = "1793278605120"                // 发送时间戳 (ms)
LR_EXPECTED_DELIVER_TS = "1793278607120"                // 期望定时触发时间戳 (ms)
校验维度 (Invariant) 统计指标字段 核对机制与判定准则 通过标准
1. 零消息丢失
(Zero Data Loss)		 unconsumedCount 所有成功发送的普通/顺序/定时/Pop 消息以及状态为 COMMITTED 的事务消息均记入期望集合，排空阶段结束后逐条核对是否已被消费确认。 == 0
2. 零数据损坏
(Zero Corruption)		 crcCorruptionCount 消费端收到 MessageExt 后对 getBody() 重新计算 CRC32，并与消息属性中的 LR_CRC32 比对，任何 1 字节翻转或截断立即告警。 == 0
3. 严格 FIFO 顺序与连续性
(Strict FIFO Order)		 fifoOrderViolationCount
fifoGapViolationCount		 按每个 shardingKey 独立维护消费水位线：实时校验到达序列是否满足 seqId == prev + 1（允许故障重启下的幂等重投 seqId <= prev），并在收尾阶段验证 [0..maxSentSeq] 无任何空洞缺失。 == 0
4. 事务回滚隔离性
(Tx Rollback Isolation)		 rollbackLeakCount 凡是通过本地事务直接返回 ROLLBACK_MESSAGE 或通过 Broker 回查返回 ROLLBACK_MESSAGE 的半消息，若被任何消费者收到，立即记为事务隔离泄露。 == 0
5. 定时触发准确性
(Timer Accuracy)		 prematureTimerDeliveryCount 核对 DELAY 消息实际消费时间 now + timerToleranceMs >= expectedDeliverTimestamp，严禁定时消息未到期提前投递。 == 0

4. 五大并发工作负载与故障注入设计

NormalMessageWorkload

使用 DefaultMQProducer 与 MessageListenerConcurrently 并发收发普通消息，验证基础 CommitLog 与 ConsumeQueue 读写链路。

FifoOrderedWorkload

使用固定队列选择器（Pinned Queue Selector）绑定多组 shardingKey 与 MessageListenerOrderly，验证 Broker 队列锁与顺序消费位点推进。

DelayTimerWorkload

通过 msg.setDeliverTimeMs() 持续发送定时消息，同时覆盖时间轮（TimerWheel）与 RocksDB Timer（RIP-82）存储引擎。

TransactionWorkload

按固定比例构造三类事务分支：70% 本地直接 Commit、20% 本地直接 Rollback、10% 返回 UNKNOW 触发 Broker 异步回查 Commit/Rollback。

PopMessageWorkload

通过 RMQPopClient 轮询集群各 Broker 节点执行 popMessageAsync 并对每条消息调用 ackMessageAsync，验证 Pop 飞行状态与 RocksDB Pop 存储。

ClusterChaosController

按配置周期（--chaos-interval）轮流对独立 Broker 进程执行优雅重启（SIGTERM）或强制杀进程（SIGKILL），并校验集群路由在超时窗口内完整恢复。

6. 执行脚本与操作指南

6.1 一键运行双存储引擎 Matrix 端到端长稳验证

bash test/bin/e2e-longrunning.sh run \
  --profile matrix \
  --duration 60 \
  --drain-timeout 30 \
  --chaos-interval 15 \
  --chaos-mode graceful \
  --send-interval-ms 25 \
  --work-dir /tmp/rmq-e2e-longrunning

6.2 单独运行 RocksDB 存储引擎 + 混合故障注入 (SIGTERM + SIGKILL)

bash test/bin/e2e-longrunning.sh run \
  --profile rocksdb \
  --duration 120 \
  --chaos-interval 20 \
  --chaos-mode mixed \
  --work-dir /tmp/rmq-e2e-rocksdb

6.3 独立进程集群手工启停与故障演练

# 1. 启动独立 NameServer + 2 节点 Broker 进程
bash test/bin/e2e-longrunning.sh start-cluster --profile rocksdb --work-dir /tmp/rmq-cluster

# 2. 查看集群各节点 OS 进程存活状态
bash test/bin/e2e-longrunning.sh status --work-dir /tmp/rmq-cluster

# 3. 手动重启指定 Broker 进程 (graceful 或 kill)
bash test/bin/e2e-longrunning.sh restart-broker --work-dir /tmp/rmq-cluster --broker-id 0 --mode graceful

# 4. 停止并清理集群进程
bash test/bin/e2e-longrunning.sh stop-cluster --work-dir /tmp/rmq-cluster
