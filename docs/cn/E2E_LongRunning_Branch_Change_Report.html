1. 这次分支在解决什么

嵌入式单测共享同一个 JVM，看不到独立 NameServer / Broker 进程、真实刷盘和 SIGTERM 重启。这个分支不改 Broker 生产代码，只在 rocketmq-test 里加一套可重复的验证入口：

  • 脚本拉起独立 OS 进程集群，存储可切 default（文件 ConsumeQueue + Config V1）或 rocksdb（RocksDB ConsumeQueue + Config V2 + Timer/事务/索引 RocksDB）。
  • 先跑 32 个功能场景，再跑 8 类持续负载，并在负载期间重启 Broker。
  • 每条消息带 CRC32、序号、事务状态和期望投递时间。CorrectnessLedger 在消费端核对，失败时写出 JSON 报告并以非 0 退出。

3. 变更结构

集群编排

test/bin/e2e-longrunning.sh 管理 NameServer 和多个 Broker 进程。命令包括 start-cluster、stop-cluster、restart-broker、status、run、run-suite。Profile 支持 default、rocksdb、matrix。

验证驱动

LongRunningTestDriver 探活集群、建 Topic，先执行 E2EScenarioSuite，再启动负载和 ClusterChaosController，最后排空并写 verification-report-<profile>.json。

六个不变量

  • 零丢失：unconsumedCount == 0
  • 零损坏：crcCorruptionCount == 0
  • FIFO 连续且有序：顺序违规和缺号都为 0
  • 事务回滚零泄露：rollbackLeakCount == 0
  • 过滤零泄露：filterLeakCount == 0
  • 定时不提前投递：prematureTimerDeliveryCount == 0

八类持续负载

Normal、FIFO、Delay、Transaction（70% 提交 / 20% 回滚 / 10% 回查）、Pop、Batch、Tag+SQL92 Filter、Retry + LitePull。Chaos 按间隔对 Broker 发 SIGTERM 或 SIGKILL，并等待路由恢复。

6. 怎么复现

bash test/bin/e2e-longrunning.sh run-suite \
  --profile matrix \
  --work-dir /tmp/rmq-e2e-suite

bash test/bin/e2e-longrunning.sh run \
  --profile matrix \
  --duration 60 \
  --chaos-interval 15 \
  --chaos-mode graceful \
  --work-dir /tmp/rmq-e2e-longrunning

JSON 报告写在 --work-dir/<profile>/verification-report-<profile>.json。任一不变量失败或场景失败时，驱动进程以非 0 退出。

7. 评审时可以看的边界

  • 生产代码没有改动。风险集中在测试脚本会启动本机 NameServer 和 Broker，并写入 --work-dir。
  • Broker 把磁盘告警比例硬限制在 0.90。数据盘占用超过 90% 时，即使脚本传入 0.99，发送仍会返回 CODE: 14。
  • 场景 30 依赖重试 Topic 的路由刷新。未提交的 1 秒刷新间隔就是为了让这条用例稳定；不带这处修改时，30 秒默认刷新会让重试消息赶不上断言窗口。
  • 设计细节仍在 docs/cn/E2E_LongRunning_Framework.md 和 docs/cn/E2E_LongRunning_Framework_Report.html。本文件只总结相对 develop 的分支差异和最新实测。
