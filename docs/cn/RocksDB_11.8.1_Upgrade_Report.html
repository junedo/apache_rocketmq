1. 背景与目标概览

在 RocketMQ 5.x 架构中，RocksDB 承担了多核心模块的状态与索引存储职责，包括：

  • ConsumeQueue 存储 (ConsumeQueueRocksDBStorage)：海量队列百万级 Topic/Queue 下的逻辑队列索引与物理偏移量映射。
  • Broker 元数据存储 V2 (ConfigStorage)：Topic 配置、SubscriptionGroup 订阅组配置、ConsumerOffset 消费位点的高可靠持久化。
  • Pop 消费状态存储 (PopConsumerRocksdbStore)：Pop 消费模式下的飞行消息状态与定时扫描。
  • 消息扩展存储 (MessageRocksDBStorage / RIP-82)：基于 RocksDB 的 Timer 定时消息、Transaction 半消息以及 Message Index 索引。

此前版本使用 rocksdbjni:8.4.4（及早期分支定制的 rocketmq-rocksdb:1.0.2）。升级至 RocksDB 11.x（11.8.1）面临三大核心挑战，也是本次评审的重点：

  1. C++ Native Shim ABI 兼容性：RocksDB 11.x 在 rocksdb::CompactionFilter 虚函数表中新增了 FilterV4 与 SupportsFilterV4，且修改了基类 Configurable::RegisteredOptions 的内存布局，若不更新原生 Shim 会导致虚表错位或 JVM 崩溃。
  2. 高并发读锁争用与内存效率：原配置全量使用 LRUCache（8 分片互斥锁），在高并发拉取与点查场景下存在明顯的 Cache 锁竞争；同时缺少对分区索引/过滤器与异步预取（async_io）的支持。
  3. JNI 边界冗余内存拷贝：ConfigStorage 与 RocksDBConsumeQueueTable 在点查和范围扫描时频繁创建堆内 byte[] 并触发 JNI 拷贝，且 ConfigStorage.iterate() 存在原生 Slice 句柄未随迭代器释放的隐患。

3.2 Compaction 热路径直通优化與多实例句柄隔离

在 RocksDB 11.8.1 的 Compaction 过程中，底层默认调用链为 FilterV4 → FilterV3 → FilterV2 → Filter（共 4 次虚函数分派）。本次改造在 CqCompactionFilter 中将判断逻辑提取为内联函数 ShouldRemove(const rocksdb::Slice&)，并在 FilterV4 / FilterV3 / FilterV2 / Filter 中全部直接调用，消除了热路径上的多层虚函数跳转。

同时，针对原实现中 CqCompactionFilterJni 使用全局唯一静态变量 NATIVE_FILTER_PTR 导致同进程多 Broker（如 BrokerContainer 模式或并发单测）互相覆盖 minPhyOffset 甚至引发 Use-After-Free 的缺陷，改造为由每个 ConsumeQueueRocksDBStorage 实例独立持有并管理自身的 nativeFilterPtr： 

// store/src/main/java/org/apache/rocketmq/store/rocksdb/ConsumeQueueRocksDBStorage.java
private volatile long nativeFilterPtr = 0L;

// postLoad() 中创建实例专属原生 Filter 并绑定至 ColumnFamilyOptions
this.nativeFilterPtr = CqCompactionFilterJni.createAndSetFilter(cqCfOptions);
CqCompactionFilterJni.setMinPhyOffset(this.nativeFilterPtr, messageStore.getMinPhyOffset());

// preShutdown() 中在 cancelAllBackgroundWork(true) 之后安全销毁当前实例的 Filter
long ptr = this.nativeFilterPtr;
if (ptr != 0L) {
    this.nativeFilterPtr = 0L;
    CqCompactionFilterJni.destroyNativeFilter(ptr);
}

3.3 存量 SST 数据向后兼容

100% 存量数据兼容： RocksDB 11.8.1 完全向后兼容由 RocksDB 8.4.4 生成的 format_version = 5 SST 数据文件、MANIFEST 以及 WAL 日志。MessageStoreConfig.rocksdbFormatVersion 默认保持为 5，支持集群零数据迁移原地升级，同時支持通过配置项按需开启 format_version = 6。

4. 核心性能优化详情

4.1 无锁 HyperClockCache 替代 LRUCache

原 RocksDBOptionsFactory 与 ConfigHelper 中所有 ColumnFamily 均使用 new LRUCache(capacity, 8, false)。LRUCache 每次缓存命中都需要获取分片 Mutex 更新链表头，在多消费线程并发拉取 ConsumeQueue 或高并发点查时锁争用严重。

RocksDB 11.x 提供了基于无锁原子 CLOCK 算法的 HyperClockCache。本次在工厂类中新增 createBlockCache(capacity, useHyperClockCache)： 

public static Cache createBlockCache(
    long capacity, boolean useHyperClockCache) {
    if (useHyperClockCache) {
        // estimatedEntryCharge=0 启用 11.x 自动动态槽位计算
        return new HyperClockCache(capacity, 0L, 8, false);
    }
    return new LRUCache(capacity, 8, false);
}

4.2 分区索引/过滤器与 ReadOptions.async_io

针对百万队列（海量 SST 文件）场景，新增 enableRocksdbPartitionedIndexFilters 支持，开启后自动启用两级索引（IndexType.kTwoLevelIndexSearch）与分区过滤器（setPartitionFilters(true)），同时默认开启 setOptimizeFiltersForMemory(true) 减少内存碎片。

在 AbstractRocksDBStorage、ConsumeQueueRocksDBStorage 与 ConfigStorage 的 ReadOptions 中默认启用 setAsyncIo(true)，使 RocksDB 在 MultiGet 与范围顺序扫描时自动执行异步预取。

4.3 ConfigStorage 点查与范围扫描 DirectSlice 零拷贝优化（含原生内存泄漏修复）

在 broker/config/v2/ConfigStorage.java 中完成了两项关键改造：

  • 点查零拷贝 (get(ByteBuffer key))：调用方传入的 key 来自 POOLED_ALLOCATOR（Netty 池化 Direct ByteBuffer）。原实现每次都分配 new byte[key.remaining()] 将 Key 拷贝到堆内再调用 db.get(byte[])。新实现直接从 POOLED_ALLOCATOR 借用 Direct ByteBuffer 调用 db.get(cfHandle, readOptions, keySlice, valueNioBuf)（底层走 JNI getDirect），当 Value 超过初始缓冲区大小时自动按返回长度扩容重试。
  • 范围扫描 DirectSlice 修复与 ManagedRocksIterator 资源闭环： 原代码在 iterate(ByteBuffer beginKey, ByteBuffer endKey) 中因 new DirectSlice(endKey) 单参数构造器在 JNI 层调用了 Slice(const char*)（遇到二进制 0x00 字节会被截断，见 facebook/rocksdb#13098），退化为每次分配 byte[] 并创建 new Slice(buf)，且该 Slice 从未关闭导致 C++ 堆内存泄漏。
    新实现采用双参数构造器 new DirectSlice(endSliceBuf, endSliceBuf.remaining()) 精确传入二进制长度（零拷贝访问 DirectBuffer 地址），并通过 ManagedRocksIterator 包装返回的迭代器，在 iterator.close() 时按严格顺序依次关闭 delegate → readOptions → upperBoundSlice。

4.4 ConsumeQueue 点查 (getCQInKV) 零拷贝优化

RocksDBConsumeQueueTable.getCQInKV() 被广泛用于消息拉取及按时间/物理偏移量二分查找（binarySearchInCQByTime / binarySearchInCQ）。由于每条 CQ Value 固定为 28 字节（CQ_UNIT_SIZE），新实现通过 ThreadLocal<Pair<ByteBuffer, ByteBuffer>> 复用 Direct Key/Value ByteBuffer，直接调用 ConsumeQueueRocksDBStorage.getCQ(ByteBuffer keyBB, ByteBuffer valueBB)（底层为 RocksDB.getDirect），彻底消除了二分查找循环中的堆内 byte[] 分配与复制。

4.5 AbstractRocksDBStorage.iterate() 释放顺序修复

在 AbstractRocksDBStorage.iterate() 的 finally 块中，原实现先关闭了 startSlice / endSlice / prefixSlice 和 readOptions，最后才关闭 iterator。由于 C++ RocksIterator 内部持有对 ReadOptions 及其 iterate_lower_bound / iterate_upper_bound Slice 的引用，先释放 Slice 会导致悬挂指针风险。现已修正为先关闭 iterator，再关闭 readOptions，最后释放各个 Slice。

8. 升级与回滚风险评估

跨平台原生 Shim 编译提示： 当前分支已完成 cq_compaction_filter.cpp 源码升级并重新编译了 macOS Universal 动态库（libcq_compaction_filter.dylib，同时包含 arm64 与 x86_64）。在合并发布至 Linux / Windows 生产环境前，需按 docs/en/Native_RocksDB.md 中的说明使用 RocksDB v11.8.1 头文件在 CI 或构建机上同步更新 libcq_compaction_filter.so、libcq_compaction_filter_aarch64.so 与 cq_compaction_filter.dll。
  • 平滑回滚能力：默认保持 rocksdbFormatVersion = 5，生成的 SST 文件与舊版保持兼容；若对 HyperClockCache 或 async_io 有特定环境调优需求，无需重新编译代码，直接通过 broker.conf 将 enableRocksdbHyperClockCache=false 或 enableRocksdbAsyncIo=false 即可热降级回原有行为。
  • 监控指标兼容性：RocksDBStoreMetricsManager 使用的所有 TickerType（如 BLOCK_CACHE_HIT、BLOCK_CACHE_MISS、BYTES_WRITTEN、BYTES_READ、READ_AMP_TOTAL_READ_BYTES）在 RocksDB 11.8.1 中完全兼容，Prometheus/OpenTelemetry 监控面板无需改动。
